## Decisions left to the maintainer (not planned)

- **What the `admin` token scope means.** `admin` can create scheduler jobs, write files under `~/app` and change
  an app's start command, so it can run code as the app and read its secrets; env values are nevertheless hidden
  from admin callers. Plan 017 only corrects the documentation. Whether to move the code-execution paths to a
  separate scope is a product decision.
- **Release provenance.** `SHA256SUMS` is produced by the same job as the binaries and is unsigned. Artifact
  attestations or cosign would close that; the mechanism is the maintainer's choice (noted in plan 018).
- **Gate releases on the Docker suite.** `release.yml` can publish binaries while `ci.yml`'s integration job for the
  same tag fails. Coupling them lengthens every release.
- **Bun version in CI.** Workflows install 1.4.2 while `mise.toml`/`package.json` pin 1.4.0; plan 018 aligns CI to
  1.4.0. If 1.4.2 was deliberate, bump the pins instead.

## Direction options (not planned; for the maintainer to weigh)

- **Outbound alerts.** Failed scheduled backups, retention failures (`forget --prune` failing is only a warning on a
  succeeded operation), certificate expiry and low disk are visible only by opening the UI; there is no outbound
  channel anywhere in the code. `apps/web/PRODUCT.md` defines success as "seeing what needs attention". A generic
  signed webhook is the cheapest first channel. Cost: a new secret to manage and a new failure mode.
- **CLI and MCP commands for app backups.** `apps/docs/docs/cli/index.mdx` says everything in the UI is also a
  `bento` command, but backup setup/run/check/unlock/keys are UI-only (`apps/docs/docs/cli/backups.mdx` admits it);
  the REST endpoints already exist, so this is mostly thin client code. `bento app clone-from-backup` exists but is
  undocumented.
- **A restore-drill operation.** `BACKLOG.md` lists SQLite restore, large-database restore and retention pruning as
  never verified live; clone-from-backup and its rollback already exist and could be combined into a scheduled
  "verify this backup restores" operation. Open questions: UIDs are never reused, disk headroom, claims. Needs a
  design spike first.
- **Sweep superseded shared build images** (`bento-build/valkey`, `bento-backup/restic`) — already an open
  `BACKLOG.md` hardening item; the grace-period sweep for runtime builds exists to extend.

## Findings considered and rejected

- **CI runs only on tags and releases:** a recorded decision in `BACKLOG.md` ("Decisions"), not a finding. Only the
  stale sentence about the Docker suite (plan 017) and the release-workflow hardening (plan 018) remain.
- **Splitting the large files** (`api/server.go`, `operations/apps.go`, `restic*.go`, `cli/commands.go`,
  `dto/dto.go`): no three-way duplication found; the CLI and MCP both go through REST, so validation lives in one
  place. Splitting would add churn without removing a drift risk.
- **Index keys in the argv and env editors:** the inputs are controlled; no values get mixed up.
- **JavaScript dependency upgrades:** versions are pinned exactly as the repository requires; no advisory data was
  available offline, so no upgrade is recommended without one.
- **Apps sharing one Docker network, no disk quota for app homes, floating base images and tool channels, the
  binding login endpoint returning a database password:** all recorded decisions (`BACKLOG.md`, `AGENTS.md`). The
  binding login endpoint's guards were checked against `AGENTS.md` and match.
- **Webhooks, git argv handling, archive import path safety, CSRF/Origin checks, scope routing, scheduler gateway
  allowlist, container hardening:** reviewed and found sound.
- **`serve` closing the store before workers finish after a shutdown timeout:** covered by startup recovery
  (`InterruptRunning`, the reconciler).
- **Pre-release `tailscale.com` / `tailcat` linked into the root binary:** accepted and documented in
  `apps/backend/AGENTS.md`; plan 018's vulnerability scan is the mitigation.

## Known gaps not turned into plans

- **Fault-injection coverage for other operation kinds.** `apps/backend/AGENTS.md` requires it for every kind; a
  grep-based survey found none for `app.provision`, `app.restart`, `app.update`, `app.publish`, `app.unpublish`,
  `binding.add`, `database.add`, `service.restart`, `dbadmin.apply`, `image.prune`, `image.sweep`,
  `image.rollout-stop`, `app.permissions`, `restic.recover` (failure path), `restic.unlock`, `restic.check`,
  `restic.key-add`, `restic.key-remove`, `restic.inspect`, `restic.refresh`. Plan 006 covers `app.prune`, the most
  dangerous one. The survey was by grep, not by reading every test body — verify before acting on the list.
- **`bun run ci` as a normal user reports success while skipping the root-only backend tests** (root `package.json`
  calls `make -C apps/backend ci` without `sudo`). A guard that fails `make ci` when not root would make skips
  visible.
- **Create and Edit app forms duplicate the runtime fields** and have drifted: Create validates relative paths
  (document root, release symlink, working directory) and Edit does not.
- **Remote-access socket race at startup** (`remoteaccess.Manager.Start` for one service from two callers): low
  confidence, narrow interleaving, not reproduced.
- **Design-system nits:** several form cells put Save in the body instead of the cell head, and about ten labels
  exceed two words (`apps/web/DESIGN.md`).
- **Whether the production bundle contains React's development build** (`bun build … --minify` without
  `--production`): could not be checked without Bun. Worth one look at a built `dist/app.js`.
