# Development and release

Contributors use Deno 2.9.3 and the committed lockfile. Production operators should prefer compiled Linux artifacts.

## Set up and verify

```sh
deno --version
deno task fmt
deno task lint
deno task check
deno task test
deno task test:integration
```

Integration tests soft-skip Docker-only behavior when the daemon is unavailable; read results rather than treating skips as live proof. Never run destructive tests against the checked-in `bento/` stack—use temporary roots.

## Layers

- `src/commands/`: parse/present and coordinate use cases.
- `src/services/` and `src/domain/`: state transitions and operation plans.
- `src/schemas/`: runtime validation of untrusted input.
- `src/platform/`: filesystem, lock, process, clock, random, assets.
- `templates/`: immutable Compose, images, config, in-container helpers.
- `tests/`: unit, contract/parity, and Docker integration behavior.

Keep dependencies flowing command adapters → services/domain → narrow platform interfaces. Domain code should not absorb terminal formatting, parsers, or unchecked external values.

## Compile and parity

```sh
deno task compile
deno task test:parity
deno task compile:amd64
deno task compile:arm64
```

The compiled executable embeds immutable templates, materializes required paths under the selected external stack root, and must work from any current directory. It must not require Deno, Node, Python, npm install, or a checkout. Identical input must yield equivalent generated bytes, state transitions, diagnostics, exits, and safety behavior in source and compiled modes.

## Permissions and dependencies

Tasks declare explicit read/write/env/run/net/sys permissions; do not document `-A` as supported default. Imports are centralized in `deno.json`, resolution is locked, and dependencies must work under `deno compile` without unmanaged lifecycle/native assumptions.

## Release checks

The repository exposes tasks for formatting, linting, typechecking, frozen dependency resolution, unit/contract and integration suites, native compile/smoke/parity, and Linux amd64/arm64 compilation. The checked-in GitHub workflow currently runs only on tags and published releases and compiles the two Linux binaries; it does not enforce all of those gates. Architecture-specific Docker image execution still needs matching runners where emulation is unavailable.

## Contributor safety

Validate every JSON/env/CLI/subprocess boundary at runtime, preserve exact schema-version behavior, avoid secrets on argv/output, use atomic files/locks for state, and add tests for rollback and destructive guards.
