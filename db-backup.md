# Database backup and restore review

Reviewed the current CLI, services, web API/UI, tests, and the contracts in `specs/01-product-spec.md`, `specs/04-proposed-product-enhancements.md`, and `specs/05-proposed-technical-improvements.md`. This is a code review and proposal, **not** a claim that a backup or restore has been tested on a live stack.

## What works today

| Data              | Backup                                                                                                                                                              | Restore / proof                                                                                                                                       | Automation                                                                |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| MySQL             | `bento backup --app APP [--database DB]` or `--all`; `mysqldump --single-transaction` with routines/triggers, private compressed artifact, partial-file publication | `bento restore --file FILE --app APP --target APP_verify`; exact `--replace TARGET` for deliberate drop/recreate                                      | Optional host-crontab schedule                                            |
| PostgreSQL        | Matching-service `pg_dump --no-owner --no-acl`, private compressed artifact, partial-file publication                                                               | Restore to a new app-namespaced database using app credentials, or exact-confirmed drop/recreate; an integration test covers restoring a new database | Optional host-crontab schedule                                            |
| Plain SQLite      | Online `sqlite3 .backup`, then compressed artifact under `backups/sqlite/APP/`                                                                                      | No Bento in-place SQLite restore; recovery requires a separately planned/manual cutover                                                               | Included in scheduled logical batches                                     |
| Litestream SQLite | Continuous S3-compatible replication when explicitly configured; `sqlite backup sync/status/verify/export`                                                          | `verify` restores a _temporary_ copy with integrity checking; `export` writes a separate file, never production                                       | Watcher runs continuously; **not** covered by the scheduled logical batch |

`bento backup schedule register --schedule '15 3 * * *' --bin /absolute/path/to/bento` is opt-in, not an automatic default. `bento backup schedule run` performs an all-database _logical-artifact_ batch, optionally uploading that batch's new files through an isolated rclone sidecar. `status` shows a private, bounded, redacted last-run record. Local retention keeps 10 matching relational dumps per database after a successful local batch. Only one logical batch runs at a time; a later failure leaves earlier completed artifacts. This is useful but not yet proof of disaster recovery. Backups do not cover `state.db`, `.env`, app homes, Redis, certificates, or all other stack data; stack export covers more but live SQLite bytes inside its tar are not consistency-guaranteed.

## Findings to address (priority order)

1. **P0 — Existing MySQL target can be modified without replacement confirmation.** `apps/cli/src/services/mysql.ts` uses `CREATE DATABASE IF NOT EXISTS` when `replaceOriginal` is absent, then imports SQL into that database. An existing database can therefore be overlaid/partially modified by a supposed verification restore. `apps/cli/src/server/domains/data/router.ts` checks that the web `confirmation` equals the target name but never passes `replaceOriginal`; the UI in `apps/web/src/features/data/DatabaseManager.tsx` says existing names are overwritten, yet MySQL overlays and PostgreSQL's plain `CREATE DATABASE` fails for existing names. Require an unused target unless a distinct explicit replacement operation is requested. Reject an existing MySQL database before any import, and use a server-enforced, fresh exact confirmation for replacement; never infer replacement from a typed target field alone. Add live tests for both engines and both CLI/web paths.
2. **P0 — Scheduled and web “all” results silently omit Litestream.** `apps/cli/src/services/database_backup.ts` skips Litestream targets; `apps/cli/src/services/backup_schedule.ts` and `apps/cli/src/server/domains/operations/router.ts` call it directly. The CLI's `apps/cli/src/use_cases/data.ts` _does_ sync Litestream for unfiltered app/all requests, but this happens after local retention and outside the logical-batch lock. A Litestream-only scheduled stack can report `succeeded` with zero artifacts without confirming replication. Give each selected binding an explicit result (`artifact-created`, `replica-synced`, or `unverified/failed`); require an enabled/reachable watcher and confirmed sync for green status, and report last restore-verification separately. Keep rclone limited to actual artifacts. See `specs/05-proposed-technical-improvements.md` T-03.
3. **P1 — SQLite local retention does not match SQLite artifact layout.** `runSqliteBackup` in `apps/cli/src/services/sqlite_local.ts` writes `backups/sqlite/APP/FILEID_TIMESTAMP.sqlite.zst`; `applyBackupRetention` in `apps/cli/src/services/mysql.ts` looks under `backups/SERVICE/DATABASE/` for `SERVICE_DATABASE_TIMESTAMP` names. Passing SQLite artifacts from `runDatabaseBackup` therefore scans `backups/sqlite/FILEID/`, not the directory actually written. SQLite dumps can grow without bound. Make retention engine-specific and keyed by app + file ID (not just file ID), with allowlisted filenames and tests for multiple apps/files, symlinks, failed batches, and low disk space. Preserve verified restore points; apply local retention only after the entire requested backup policy succeeds.
4. **P1 — Success and failure evidence is too weak for unattended recovery.** A nonempty dump and a successful `rclone copyto` exit code are not integrity/restore checks. `last-run.json` stores the last attempt, counts, and bounded names, not per-binding coverage, checksum, remote verification, or last _successful_ recovery point. An all-empty stack reports success; an interrupted cron job can leave `running` indefinitely. The cron fragment redirects stdout/stderr to `/dev/null`, so monitoring must poll `status` and check freshness; the status command currently exits 0 even for a failed/stale last run. Record separate last-attempt and last-success timestamps, target inventory and per-target status; distinguish `missing`, `stale`, `unverified`, and `verified`, with configurable RPO/age thresholds and a nonzero health exit for alerts. Write atomic private SHA-256 manifests, verify remote readback/checksum where available, and schedule isolated restore drills. An upload is _transport evidence_, not remote durability.
5. **P1 — Scheduled status can misrepresent overlapping attempts.** `runScheduledBackup` writes `running` before acquiring the batch lock inside `runDatabaseBackup`. If a second run overlaps, it writes `failed` while the first is still running (and may later overwrite that record with `succeeded`). Acquire the schedule/batch operation lock before recording an attempt and use run IDs plus separate attempt history or an atomic compare/update so a rejected overlap cannot mask a legitimate run.
6. **P1 — Production restore needs a safer workflow, not just a confirm flag.** Relational replacements drop/create before import and are non-atomic; PostgreSQL terminates active sessions, but neither path proves a fresh rollback copy or drains all app writers. MySQL's `--single-transaction` does not make concurrent DDL or non-transactional tables safe, and per-database dumps do not give a shared cross-database snapshot. Offer `prepare` (source/provenance/engine/compression/checksum validation, free-space check, new namespaced staging DB, test import and app checks) followed by a short, deliberate `cutover` (stop managed writers, exact fresh approval, recoverable rollback artifact, post-checks); on failure, leave the app disabled and provide recovery instructions. Do **not** auto-replace production as part of auto backup or a drill.
7. **P1 — No guarded SQLite production cutover.** `sqlite backup verify/export` is intentionally non-destructive, but recovering a live WAL-mode file is manual and error-prone. Implement `sqlite restore prepare/cutover/rollback` as proposed in `specs/04-proposed-product-enhancements.md` F-02: private same-filesystem staging, `integrity_check`, checksum-bound expiring plan, writer drain, preserved live database and WAL/SHM rollback set, ownership/mode repair, exact confirmation, and explicit disabled-until-verified state. Never replace a SQLite file while managed or external writers are active.
8. **P2 — Backup/restore/transfer concurrency and full-stack scope.** The logical backup has its own lock, but restore and stack export/import do not share a documented data-operation conflict policy. Export stops relational/Redis services for raw copies but can archive live SQLite files and minicrond SQLite registries/WAL inconsistently. Add a stack operation conflict matrix (T-05), take SQLite-aware snapshots for transfer (T-04), and test concurrent WAL writes. Offer separate inventory/status for essential non-database assets; do not present `backup --all` as a complete stack backup.
9. **P2 — Restore source selection and browser feedback.** The web lists `*.sql`/`*.sqlite` by extension via a recursive `stat` walk in `apps/cli/src/use_cases/data.ts`; restore resolves a path below `backups/` but does not verify the artifact's binding, content, checksum, or non-symlink provenance. Filter to regular, finalized, non-symlink artifacts via `lstat`, avoid traversing symlink directories, bind artifacts to manifest/engine/app/service, and show only compatible sources and valid _new_ targets. Reject unknown sources unless an explicit trusted external-import path is used. Show a clear “this will not change production” verification flow and a separately gated “replace production” flow with downtime/partial-failure warnings.

## Proposed user experience for safe auto backup

1. **Setup:** Show every database binding and its recovery method, coverage gaps, expected interval, disk budget, destination, and whether the runner/crontab/rclone/watcher is reachable. Default to _opt-in_, especially for remote destinations. Offer a wizard/CLI plan that configures an off-host target (prefer encrypted, access-scoped, versioned/immutable remote storage), performs a dry-run preflight, installs the host schedule, and runs one real backup plus test restore before calling it ready. For container deployments, explicitly require a host-managed scheduler; do not imply crontab registration works inside the Bento container.
2. **Policy:** Per stack, let operators choose cron time/timezone, per-binding inclusion, max age/RPO, local retention by age/count/bytes, minimum free-space reserve, remote retention policy, verification cadence, and alert destination. Explain that Litestream retention and rclone remote retention are separate policies. Retain at least one known-good local and off-host recovery point when feasible; only prune after a new complete, verified policy checkpoint. Prevent auto jobs from reusing a production target.
3. **Run:** Preflight disk, permissions, mounted paths, credentials, services, destination, and selected bindings. Lock the _whole_ batch including Litestream sync and upload evidence; create unique batch IDs and private partial files; record one result per binding. Publish a versioned manifest with hashes and tool versions only after successful dump creation; upload current batch artifacts/manifest and confirm visibility or readback. Keep earlier artifacts if a later target fails, record partial coverage as failure, and retry transient upload errors without rerunning destructive steps.
4. **Monitor:** Display a recovery dashboard per binding: latest local point, off-host point, hash/readback status, Litestream last sync _versus_ last verified restore, last drill, age vs policy, disk use, and last failure. Provide nonzero health-check/JSON output and alert on missing targets, failures, stale evidence, low space, or replica lag. Do not call a schedule successful merely because it ran or uploaded.
5. **Drill and recover:** Regularly fetch a copy from the remote destination, restore to a disposable DB/file, run integrity and application-level smoke checks, then clean up the temporary target. Keep a short private audit record. For real recovery, guide an operator through source selection, preview/checksum, new-target restore and validation, planned outage, explicit cutover/rollback, and post-restore checks. No automatic production restore.

**Suggested delivery:** (1) Fix existing-target refusal and misleading web confirmation, SQLite retention, and Litestream schedule coverage; add regression tests. (2) Add per-binding manifests/status, health exits/alerts, remote evidence, and recurring non-production drills. (3) Ship two-phase relational/SQLite recovery and transfer/lock improvements, with Docker integration tests for MySQL, PostgreSQL, and concurrent SQLite WAL writes. These changes should preserve the existing exact-confirmation, private-file, source/compiled, and loopback-safety contracts.

## What an operator can do now

- Configure a host schedule and off-host rclone destination per `docs/src/content/docs/guides/data/backup-restore.md`, then run `bento backup schedule run` and inspect `bento backup schedule status`; monitor freshness externally, not just its exit code. Check that every expected MySQL/PostgreSQL/plain-SQLite artifact exists; **check Litestream separately** with `bento sqlite backup status --app APP`, `bento sqlite backup sync --app APP`, and `bento sqlite backup verify --app APP`.
- Copy and protect `state.db`, `.env`, app homes, Redis data, certificates, and other durable assets separately using consistency-safe methods; do not trust a live `stack.tar.gz` as a SQLite backup. Regularly test restoring an **unused** namespaced relational verification database and inspect app-level invariants. Do not use a web restore to replace an existing database until the confirmation/behavior mismatch is fixed.
- Watch disk use under `backups/sqlite/` until SQLite retention is repaired. Off-host copies, restore tests, and alerts are operator responsibilities today.
