---
title: Scheduler
description: Cron jobs and long-running workers for an app.
---

Every app has its own scheduler ([minicrond](https://github.com/khanhicetea/minicrond)) running inside its container,
as its own user. The **Scheduler** tab is its full UI: create jobs and workers, run a job now, and read run history and
logs.

- **Jobs** run on a cron schedule — e.g. `php artisan schedule:run` every minute.
- **Workers** run continuously and are restarted if they exit — e.g. `php artisan queue:work`.

<Callout type="note">
The app must be **running** to manage its jobs. Jobs keep running while the app is unpublished; stopping or restarting
the app stops or restarts them too.
</Callout>

## Commands and environment

Write the command as a **Command** (a shell line), e.g. `php artisan schedule:run`. New jobs and workers start in
`~/app` with the app's environment — `PATH` with the toolchain, `DB_*`, `REDIS_*` (when Valkey is on), and your env
vars — so Laravel needs no `.env` database settings. A value you set on the job or worker wins.

The **Argv** form also works with bare names such as `["php", "artisan", "queue:work"]`: they are looked up in
`/usr/local/bin`, `/usr/bin`, and `/bin`. Example worker for Laravel:

```toml
[[worker]]
name = "queue-default"
argv = ["php", "artisan", "queue:work", "--sleep=1", "--tries=3", "--max-time=3600"]
```

Prefer **Argv** for a worker that is a single program. A **Command** runs under `/bin/sh` (dash in Bento's images),
which stays alive beside the program for the whole run: one extra process of about 400 KiB per worker. If you need
shell syntax, start the program with `exec`, e.g. `cd sub && exec php artisan queue:work`. Stops and timeouts reach the
program either way.

Workers are restarted after every clean exit, so `php artisan queue:restart` in a deploy script is enough to load new
code. A worker that keeps failing (non-zero exit within 30 seconds, 5 times in a row) is stopped and shown as
**Exhausted** in the **Scheduler** tab; fix it, then start it again there or with
`bento app minicrond <slug> -- start <worker>`.

Things to know:

- Jobs belong to the app (stored in its home), so they're included in [app backups](/apps/backup).
- A job can never run twice at once, even while the container is being replaced.
- Tasks named `zz-bento-*` are Bento's own (e.g. weekly SQLite `VACUUM`) and read-only.
- After a deploy, restart queue workers (`php artisan queue:restart`) so they load the new code.

## Turn it off

An app that needs no jobs or workers can run without a scheduler: clear **Scheduler (minicrond)** in the app's
[Container settings](/apps/settings#valkey-and-scheduler), or set `minicrond` to `false`. The running container is replaced. While it is off:

- nothing runs — not your jobs and workers, and not Bento's own `zz-bento-*` tasks such as the SQLite `VACUUM`;
- the **Scheduler** tab and the scheduler API answer that minicrond is off for this app;
- your jobs stay in the home and run again when you turn it back on.
