---
title: Scheduler
description: Cron jobs and long-running workers for an app.
---

Every app has its own scheduler ([minicrond](https://github.com/khanhicetea/minicrond)) running inside its container,
as its own user. The **Scheduler** tab is its full UI: create jobs and workers, run a job now, and read run history and
logs.

- **Jobs** run on a cron schedule — e.g. `php artisan schedule:run` every minute.
- **Workers** run continuously and are restarted if they exit — e.g. `php artisan queue:work`.

<Callout type="note">
The app must be **running** to manage its jobs. Jobs keep running while the app is unpublished; stopping or restarting
the app stops or restarts them too.
</Callout>

## Commands and environment

Write the command as a **Command** (a shell line), e.g. `php artisan schedule:run`. New jobs start in `~/app` with the
app's environment — `PATH` with the toolchain, `DB_*`, `REDIS_*`, and your env vars — so Laravel needs no `.env`
database settings.

| Field | Jobs | Workers |
| --- | --- | --- |
| Environment | the app's (`env_base = inherit`) by default | set **Environment base** to `inherit` yourself |
| Working dir | `~/app` by default | set it to `~/app`, or use absolute paths |
| Argv form | absolute paths only, e.g. `/usr/local/bin/php` | same |

A worker left on the `clean` environment sees only `PATH=/usr/bin:/bin`: `php` is not found and no database credentials
are set. Example worker for Laravel:

```toml
[[worker]]
name = "queue-default"
command = "php artisan queue:work --sleep=1 --tries=3 --max-time=3600"
env_base = "inherit"
working_dir = "~/app"
```

<Callout type="warning" title="Check workers after a deploy">
`php artisan queue:restart` makes workers exit so they reload code, and the current scheduler does not always start
them again. Check the worker is running in the **Scheduler** tab after a deploy. If it is stopped, start the workers
again with `bento app minicrond <slug> -- reload`. The [deploy script recipes](/apps/deploy-scripts) end with
`sleep 3 && minicrond reload`, which does this after every deploy.
</Callout>

Things to know:

- Jobs belong to the app (stored in its home), so they're included in [app backups](/apps/backup).
- A job can never run twice at once, even while the container is being replaced.
- Tasks named `zz-bento-*` are Bento's own (e.g. weekly SQLite `VACUUM`) and read-only.
- After a deploy, restart queue workers (`php artisan queue:restart`) so they load the new code.
