---
title: App backups
description: Encrypted snapshots of a whole app, restored as a new app — on this server or another.
---

An app backup is a [restic](https://restic.net) snapshot of an app's home (code, uploads, `.env`), its databases, its
scheduled jobs, and a description of its settings. Snapshots are encrypted and deduplicated — after the first one,
only changes are uploaded.

Set it up from the app's [Backup tab](/apps/backup#app-backup).

Snapshots are encrypted with the [stack backup password](/backups#stack-backup-password). Keep a copy of it off the
host.

## What gets saved

1. A plain SQL dump of each MySQL and PostgreSQL database (taken first, so every upload referenced by the data is
   included).
2. Safe copies (SQLite `.backup`, never a raw copy of a live file) of every SQLite database in the saved paths —
   files named `*.sqlite`, `*.sqlite3`, `*.db`, `*.db3`, `*.s3db` or `*.sl3`, outside `.git`, `node_modules`,
   `vendor` and your excludes — plus any other file you list under **SQLite files**, and the scheduler's jobs.
3. `app.json` — runtime, resources, domains, bindings, git source, the Valkey and scheduler settings, and environment
   variables **with secrets redacted**.
4. The home folder, minus your excludes — including the app's [Valkey](/apps/data#valkey) snapshot, `dump.rdb`, when
   it has one.

The app keeps running throughout.

### Include secrets

By default no passwords are saved. Turn on **Include secrets** in **Backup settings** to also store environment
secrets and database passwords inside the (encrypted) snapshot, so a restored app works without re-entering them.

## Restore

A whole app backup is **never** restored over the live app. Pick a snapshot and press **Clone** to restore it into a
new app, giving it a new slug (e.g. `shop-restored`). Type `clone <new-slug>` to confirm. The new app is created
**stopped**, so you can check it before publishing or moving domains.

To roll back only one database of the live app, press **Restore DB** on the snapshot instead — see
[Restore a database](/backups/database).

## Restore on another server

Useful for migrations and disaster recovery.

<Steps>
  <Step title="Get a key for the repository">
    Either the source stack's backup password (`sudo bento backup password` on the source server), or an extra key:
    in the source app's Backup tab, **Access keys → Add** and type `export <slug>`. Copy the key — it's shown once.
  </Step>
  <Step title="Add the same rclone remote on the new server">
    See [Off-site storage](/backups/rclone).
  </Step>
  <Step title="Restore">
    **Apps → From app backup**, enter the repository and key, and choose a slug. The new server needs a database
    server of the same engine and version. Leave the key empty (or, with `bento app restore-from-backup`, leave
    out `--key-file`) to use the new stack's own backup password — useful when both stacks share one.
  </Step>
</Steps>

## Keep an eye on it

- **Backups → App backups** shows each app's last run, next run, and verification.
- A run that couldn't read some files is marked **partial**.
- **Verify** reads part of the data back to check the repository is healthy.
- If a run warns about a stale lock, fix the remote's delete permission and press **Remove stale locks**.

<Callout type="danger">
Lose the stack backup password and every other key, and the backups cannot be recovered. Store them in a password
manager, away from the server.
</Callout>
