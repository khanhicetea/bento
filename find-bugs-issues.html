H1HighClone/restore follows symlinks inside the restored snapshot, so it can read or move host files as rootoperations/restic_clone.go

Where

  • Dump restore loop (~L1005): platform.ContainedPath(bentoDir, d.File) → RestoreSQLite/RestoreRelational → Decompress → os.Open (follows symlinks)
  • restoreHomeSQLite (~L1308): IsSQLiteFile uses O_NOFOLLOW on the last component only; CopyFile follows symlinked parent dirs
  • installRestoredHome, partial-paths branch (~L1227–1247): rename(restoredHome/p → home/p) with NoSymlinkBetween checked only on the destination side

Attack flow

crafted repo→restic restore→bento/sqlite/x.db → /stack/bento.db→RestoreSQLite (header OK)→state DB readable by clone tenant
  • A symlinked bento/sqlite/*.db copies bento.db or another app's SQLite DB into the clone.
  • A symlinked bento/home-sqlite copies any host SQLite file into the clone home, owned by the clone UID.
  • A symlinked SQL dump pipes a host file into mysql/psql; the stderr tail lands in the operation error shown in the UI.
  • A manifest path through a symlinked dir (x → /etc, path x/passwd) moves the host file into the tenant home.

Reachability

Directly reachable through Restore from app backup (another stack's repo, app.restore-from-backup). Anyone with that repo's key and write access can craft the snapshot.

Fix

  • After restore, walk backup/bento and reject any symlink or non-regular file.
  • Read inputs with openat2(RESOLVE_NO_SYMLINKS|RESOLVE_BENEATH) or NoSymlinkBetween(bentoDir, p).
  • Require NoSymlinkBetween(restoredHome, src) before every partial-path rename.
M1MediumAn interrupted clone leaves a partial app; its recovery path is dead code; plaintext staging data and job containers stay behindrestic_clone.go:830 · reconcile.go:609
  • AppID is "allocated at submission so an interrupted attempt can be recognized", but InterruptRunning never replays ops and every resubmit gets a new AppID. The prev.ID == req.AppID → rollbackClone branch can never run.
  • A crash after create-app leaves a half-built app. Its slug is taken (a resubmit fails with slug-taken), and removal keeps the home and databases, so the slug stays blocked until a prune.
  • staging/restic-<opID>/ keeps the decrypted snapshot, plain SQL dumps and secrets.json forever. homes/.clone-* and staging/home-sqlite-* also leak.
  • Job containers run sleep 86400/3600. collectTools removes only non-running containers, so an orphaned restic process can hold repo locks for up to 24 h.

Fix

In Recover: roll back interrupted clone/restore ops using the request's AppID, sweep staging/restic-*, home-sqlite-* and .clone-* whose op is terminal, and collect running RoleBackup containers whose op is terminal or missing.

M2MediumA clone can put two bindings on one service with the same DB user, so one binding gets the wrong passwordrestic_clone.go:510–560

pickCloneService falls back to "same engine + version". Two source bindings on different MySQL 8 services can therefore map to one local service. Both get Username = "u"+AppID with different passwords. CREATE USER IF NOT EXISTS keeps the first password, so the second binding's BENTO_DB_* credentials fail. The DB-name collision check only looks inside a single binding. AddBinding refuses this case; planClone does not.

Fix

Track the services already used in planClone: block or merge, and check DB-name collisions across all bindings.

M3MediumspecVersion 2→3 recreates every running app container on upgraderuntime/spec.go:112

HomePath already changes the fingerprint through mounts, HOME= and the identity hash. For existing apps (HomePath=="") the shape is identical, but the bump changes every io.bento.generation. The reconciler then sees DriftReplace for every running app: a stack-wide rolling restart with no shape change behind it.

upgrade→fingerprint differs→DriftReplace ×N→all apps restarted

Fix

Revert to specVersion = 2. TestHomePathChangesContainerPathsOnly already shows the fingerprint changes without the bump.

M4MediumThe secret-env check misses common credential names, which leak into app.json and logsdomain/restic.go:252–264

Only _KEY, SECRET, PASSWORD and TOKEN (plus a KEY suffix) count as secret. DATABASE_URL, REDIS_URL, *_DSN, *_PASS, *_PWD, *_CREDENTIALS, *_AUTH, PRIVATE_*, *_SALT are stored in plain text in every snapshot's app.json, even with Include secrets off (the default). They are also not redacted from operation output, which breaks AGENTS rule 6.

The opposite also happens: CACHE_KEY_PREFIX and SORT_KEY are emptied on clone (L6).

Fix

Widen the list, redact URLs that carry userinfo, and consider operator-marked secret keys.

M5MediumClone/restore holds the global claim for the whole snapshot download, freezing the stackoperations/claims.go

app.clone-from-backup and app.restore-from-backup are global, and they include the full restic restore, which can take hours. Deploys, webhooks and starts queue up behind it, and scheduled backups are recorded as skipped.

Fix

Split it in two: a download op that claims only restic:<src>/restic-remote:<repo>, then a short global materialize op. Until then, warn in the UI that other operations will wait.

M6MediumRestic job containers die after 24 h (sleep 86400), killing long backups and restoresbackup/restic.go:104, :343

Every restic command is an exec inside a container whose PID 1 is sleep 86400. A first upload of a large home, a check, or a clone restore longer than 24 h gets killed, leaving a stale repo lock and a confusing error. The home-SQLite helper has the same problem with sleep 3600.

Fix

Use sleep infinity. Lifetime is already bounded by job.Close and the orphan collection from M1.

M7MediumAfter bento import, restic settings say "schedule enabled" while the schedule row is disabledstack/import.go:210 · api/restic.go:48

Import disables the schedules rows but leaves restic:<app> schedule.enabled=true. nextResticRun reads the settings, so the UI shows "Next run in …" for a backup that never happens. The next settings save silently turns it back on. The imported stack also inherits the repo key and state, so two stacks can write to the same repository without the operator knowing.

Fix

Clear schedule.enabled inside restic:* settings in rewriteImportedState, derive nextRun from the schedule row, and show an "imported, still connected" notice.
