## 🔴 High

### H1. Restoring follows symlinks inside the snapshot → reads or moves host files as root

**Where:** `apps/backend/internal/operations/restic_clone.go`
- the dump restore loop (`dump, perr := platform.ContainedPath(bentoDir, d.File)` ~L1005 → `deps.RestoreSQLite` / `deps.RestoreRelational` → `backup.Decompress` → `os.Open`)
- `restoreHomeSQLite` (~L1308): `IsSQLiteFile(src)` uses `O_NOFOLLOW` on the **last component only**; `platform.CopyFile` then follows symlinked parent directories
- `installRestoredHome`, partial-paths branch (~L1227-1247): `src := filepath.Join(restoredHome, p)` → `renameNoCross(src, dst)`. `NoSymlinkBetween` is checked on the **destination** (`home`) side only, never on `restoredHome`.

**Problem.** `restic restore` recreates symlinks exactly as they are stored in the snapshot. Every path the clone code reads afterwards is checked only lexically (`platform.ContainedPath`). It is never checked for symlinks. `rejectSpecialFiles` runs on `home/` only, not on `bento/`. A crafted snapshot can therefore:

1. Set `bento/sqlite/x.db` (or a dump's directory) to a symlink to `/<stack-root>/bento.db` or another app's `sqlite/<id>/` file. `RestoreSQLite` only checks for the "SQLite format 3" header, so the **whole Bento state DB** (session hashes, binding passwords, Redis ACL passwords, settings) gets copied into the clone's SQLite directory, where the clone's tenant can read it.
2. Set `bento/home-sqlite` to a symlinked directory. `restoreHomeSQLite` then copies any SQLite file on the host into the clone home, owned by the clone UID.
3. Make a relational dump a symlink to any host file. It is piped into `mysql`/`psql`, and the error tail (up to 4 KiB of stderr) is copied into the operation error that the UI shows, so file contents leak.
4. Make a manifest `paths` entry go through a symlinked directory in the restored home (`x -> /etc`, path `x/passwd`). `rename()` follows intermediate symlinks, so the host file is **moved** into the tenant's home when staging and the target share a filesystem. The host file is gone and the tenant now owns the directory that holds it.

**Reachability.** You can reach this most directly through **Apps → New → From app backup / `bento app restore-from-backup`** (`app.restore-from-backup`). There the operator points Bento at a repository it did not write, and anyone with that repo's key and write access can craft the snapshot. Snapshots of this stack are generated by Bento, so the `bento/` tree is trusted for them. The home tree is still tenant-controlled, though.

**Fix.**
- After `restic restore`, walk `backup/bento` and reject **any** symlink or non-regular file (`rejectSpecialFiles`, extended to symlinks for that tree).
- Open every Bento-dir input with `openat2(RESOLVE_NO_SYMLINKS|RESOLVE_BENEATH)` (or `O_NOFOLLOW` on each component). `NoSymlinkBetween(bentoDir, path)` before reading also works.
- In the partial-paths branch, require `NoSymlinkBetween(restoredHome, src)` before renaming.

## 🟠 Medium

### M1. An interrupted clone leaves a partial app; the "cleanup on retry" path can never run

**Where:** `restic_clone.go:830` (`runClone`), `restic_clone.go:215` / `restic_remote.go` (`AppID: platform.NewAppID()` at every submission), `controller.go Recover`, `store.InterruptRunning`, `reconcile.go:609` (`collectTools`).

- `ResticCloneRequest.AppID` is documented as "allocated at submission so an interrupted attempt can be recognized and cleaned up". But `InterruptRunning` **never replays** operations, and every resubmission allocates a **new** `AppID`. So the `prev.ID == req.AppID → rollbackClone` branch is unreachable.
- A backend crash/restart in the middle of a clone (after the `create-app` transaction) leaves the following behind:
  - an app row (`provisioned`) with half-restored databases and home;
  - the new slug, now taken. A resubmit fails with *slug-taken*, and `app remove` keeps the home and databases, so the slug stays blocked until a prune.
  - `staging/restic-<opID>/` holding the **decrypted snapshot, plain SQL dumps and `secrets.json`**, with nothing ever deleting it. `staging/home-sqlite-*` and `homes/.clone-<opID>` are also left behind.
  - restic job containers (`sleep 86400`) and home-sqlite containers (`sleep 3600`) that keep **running**. `collectTools` only collects *non-running* containers, so an orphaned `restic backup` can keep running against the repo for up to 24 h, and later `forget --prune` (exclusive lock) fails with exit 11.

**Fix.** On `Recover`, find interrupted `app.clone-from-backup` / `app.restore-from-backup` ops. Run `rollbackClone` for their `AppID` (it is in the request). Remove `staging/restic-*`, `staging/home-sqlite-*` and `homes/.clone-*` whose op is terminal. Let `collectTools` also remove *running* `RoleBackup` containers whose `LabelOperation` op is terminal or missing.

### M2. A clone can create two bindings on the same service with one username

**Where:** `planClone`, `restic_clone.go:510-560`; `pickCloneService` falls back to "any service with the same engine+version".

If the source app had two MySQL (or PG) bindings on different services of the same version, and this stack has only one such service, both bindings land on the **same** service. Both get `Username = "u"+AppID` but **different** random passwords. `dataservices` runs `CREATE USER IF NOT EXISTS …` (and the PG equivalent), so the second binding's password is never applied, and the app's `BENTO_DB_*` env for that binding fails to authenticate. The "collide" check (`slices.Contains(b.Databases, target)`) only looks inside one binding, so two bindings can also both claim the same target DB name. The normal `AddBinding` path refuses a second binding to the same service. The clone path does not.

**Fix.** In `planClone`, track the services already used and either block ("two source bindings map to service X") or merge them into one binding. Check DB-name collisions across all bindings of the clone.

### M3. `specVersion` 2→3 recreates every running app on upgrade

**Where:** `apps/backend/internal/runtime/spec.go:112`

`HomePath` already reaches the fingerprint through `appMounts` (target), `appEnv` (`HOME=`) and the identity hash. For existing apps (`HomePath == ""`) the container shape is byte-identical. Bumping `specVersion` still changes **every** app's `io.bento.generation`. After the upgrade, `reconcile` sees `DriftReplace` for every running app and submits `app.reconcile` for each one. That is a stack-wide rolling restart (downtime for every app) with no shape change behind it. The test `TestHomePathChangesContainerPathsOnly` already proves the fingerprint changes without the bump.

**Fix.** Revert to `specVersion = 2`, unless another shape change in this branch needs it (none found).

### M4. The secret-env check misses common credential names

**Where:** `apps/backend/internal/domain/restic.go:252-264` (`SensitiveEnvKey`), used by `redactedEnv` (app.json), `resticSecrets`, `secretRedactor` (operation output) and `planClone`.

Only keys containing `_KEY`/`SECRET`/`PASSWORD`/`TOKEN` or ending in `KEY` are treated as secret. That misses `DATABASE_URL`/`REDIS_URL`/`*_DSN` (connection strings with an embedded password), `*_PASS`, `*_PWD`, `*_CREDENTIALS`, `*_AUTH`, `PRIVATE_*`, `*_SALT`, `*_COOKIE`, and others. With **Include secrets OFF** (the default, sold as "no secrets in the backup"), these values are stored in plain text in every snapshot's `app.json`. They are also not redacted from operation errors or warnings, which breaks AGENTS rule 6 ("Secrets never go in … logs, errors").

The opposite case also bites. `CACHE_KEY_PREFIX`, `SORT_KEY`, `MONKEY` are treated as secrets, so a clone **empties** them unless secrets were included.

**Fix.** Widen the list (`PASS`, `PWD`, `DSN`, `URL` with userinfo, `AUTH`, `CREDENTIAL`, `PRIVATE`, `SALT`, `COOKIE`, `CERT`). Also redact any value that parses as a URL with userinfo. Consider letting the operator mark keys explicitly.

### M5. Clone/restore holds the global claim for the whole download

**Where:** `operations/claims.go` (`app.clone-from-backup` / `app.restore-from-backup` are not classified, so they are global)

The global op contains `restic restore` of the whole snapshot, which can take hours for a large home. During that time **nothing else runs**: deploys, webhooks, starts and stops wait in the queue, and scheduled DB/app backups are recorded as `skipped`. Only the create-app/provision/import steps really need exclusivity.

**Fix.** Split it into two ops: a download op that claims only `restic:<src>` / `restic-remote:<repo>`, writes into its own staging and needs no global claim, followed by a short global "materialize" op. As a smaller step, keep it global but document the freeze in the UI ("other operations wait").

### M6. Restic job containers live at most 24 hours

**Where:** `apps/backend/internal/backup/restic.go:104-105` (`sleep 86400`) and `:343-344` (`sleep 3600` for home-SQLite).

Every restic command runs by `exec` inside a container whose PID 1 is `sleep 86400`. A first backup of a large home over a slow uplink, a `check`, or a clone `restore` that takes longer than 24 h is killed when `sleep` exits. The repo is left with a stale lock and the operation fails with a confusing exec error.

**Fix.** Use `sleep infinity` (the rclone image is Alpine/BusyBox, which supports it) or `tail -f /dev/null`. Lifetime is already bounded by `job.Close` and by the M1 orphan collection.

### M7. After an import, restic settings show "schedule enabled" while the schedule is off

**Where:** `stack/import.go:210` disables `schedules` rows. `restic:<appId>` settings keep `schedule.enabled = true`. `api/restic.go:48` `nextResticRun` reads the **settings**, not the schedule row.

On an imported stack, the Backup tab and `/backups/apps` show "Next run in …" and `scheduleEnabled: true`, but no backup ever runs. The next settings save silently turns it back on. The imported stack also inherits `secrets/restic/<app>.key` and `restic-state` (the repo stays "initialized"), so two stacks can write into the same repository without the operator knowing. Retention is scoped per stack tag, so data is safe, but nobody chose this.

**Fix.** In `rewriteImportedState`, set `schedule.enabled = false` inside each `restic:*` setting. Better: derive `nextRun`/`scheduleEnabled` from the schedule row. Consider showing an "imported, still connected to <repo>" notice.

## What looked solid

- Keys never reach argv, env, labels or requests. They travel only as pending files, `0400`, under `secrets/restic`, with a startup sweep.
- Exact confirmations (`clone <slug>`, `export <slug>`) are enforced server-side.
- The rollback path checks ownership through labels, the sidecar, UID ownership and `stack-id`, and burns the UID.
- The migration is transactional, re-checks the version inside the transaction, and keeps `CheckCompatible` read-only.
- Errors and streamed output are redacted with `secretRedactor` / `cloneSecretRedactor` (limited by M4).
- Claims: `restic.backup` shares the app and its services, stays exclusive on the repo, and uses a pool of 2.

4. **M2, M4, M7**, then **M5** (split the op) when convenient.
